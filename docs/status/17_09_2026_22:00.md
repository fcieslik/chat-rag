Status: ✅ DONE

Utworzono osobny CloudWatch Log Group:

/aws/apigateway/chat-rag-api

Nie używamy do tego istniejącego:

/ecs/chat-rag-api

bo ten jest przeznaczony dla ECS.

API Gateway posiada skonfigurowany dostęp do CloudWatch Logs poprzez IAM Role:

APIGatewayCloudWatchLogsRole

z odpowiednią policy:

AmazonAPIGatewayPushToCloudWatchLogs

Access logging jest włączony.

Format logów:

{
"requestId": "$context.requestId",
  "ip": "$context.identity.sourceIp",
"method": "$context.httpMethod",
  "path": "$context.resourcePath",
"status": "$context.status",
  "responseLength": "$context.responseLength",
"waf": "$context.wafResponseCode"
}

Test zakończył się sukcesem.

Przykładowy log:

{
"requestId": "3fc16143-b70d-42e7-a62e-536655d60361",
"ip": "178.43.246.12",
"method": "GET",
"path": "/health",
"status": "304",
"responseLength": "0",
"waf": "WAF_ALLOW"
}

To potwierdza, że:

API Gateway logging → CloudWatch
WAF → request allowed

działają.

Celowo NIE włączono:
Data tracing: OFF
Detailed metrics: OFF
X-Ray: OFF

Nie chcemy na tym etapie niepotrzebnie logować request/response body ani rozbudowywać observability.

LLMOps ⏳ 17. Zasady dalszej pracy
Nie tworzyć ponownie istniejących zasobów.
Nie przywracać publicznego ALB.
AWS Console jest obecnie głównym sposobem nauki/deploymentu — bez Terraform na tym etapie.
Przy instrukcjach AWS najpierw sprawdzać aktualną dokumentację, nie zgadywać na podstawie starego UI.
Instrukcje mają być krótkie i krokowe.
Po zakończeniu Cognito i CI/CD kończymy etap infrastruktury AWS.
Następnie priorytetem jest rozwój samej aplikacji AI, a nie dokładanie kolejnych usług AWS.
Jeśli później będziemy potrzebować IaC, można wrócić do istniejącej architektury i odtworzyć ją np. Terraformem/CDK — ale nie jest to teraz celem.
